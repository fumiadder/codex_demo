命令：`python3 scripts/ops_qa.py`。最终运行退出码 `0`，使用唯一项目 `opsqae070a805`、临时目录和假账号/假媒体，完成后清理自己的容器、网络、镜像标签与卷；未停止其他 Docker 服务。

| 检查 | 实际结果 |
| --- | --- |
| 新卷首次发布 | 应用容器真实构建并 healthy；`invite`、`persistent`、关闭测试模式检查通过 |
| 从版本 A 更新到 B | 账号数量、记录、上传文件 SHA-256 与睡前音频缓存 SHA-256 保持一致 |
| 发布前一致性快照 | 先完成镜像 build，再停止应用；SQLite/WAL/全部数据目录统一复制，数据库完整性、逐文件校验和及媒体引用均通过 |
| 恢复到全新卷 | 恢复数据与发布前数据一致；活动卷不变 |
| 已存在目标卷 | 明确拒绝覆盖 |
| 故意坏镜像的健康失败 | 自动回退到版本 B 的不可变旧镜像，旧应用恢复 healthy，`current-sha` 仍为 B |
| 发布备份后的新写入 | 在坏镜像替换后向数据库提交新记录标题；回退后该写入仍存在，未恢复旧数据库 |
| 睡前模块结构变化 | 修改 `bedtime.SCHEMA` 后，更新在停止活动应用前返回拒绝；活动数据与应用保持正常 |
| schema helper 错误 | 故意放入语法错误后更新立即失败；没有吞掉错误或触碰活动应用 |
| 损坏快照 | 改写一个备份上传文件后拒绝恢复，连恢复目标卷也没有创建 |

演练中发现并修正了快照连接问题：SQLite 连接的 `with` 只提交事务、不关闭连接，延迟清理 WAL/SHM 会使已生成的校验清单失效。现在复制快照先 checkpoint 并显式关闭连接，再计算哈希；校验以只读 immutable 方式打开已静止数据库。失败备份会重新启动此前运行中的旧应用。

## 配置、发布包与工作流

- `docker compose config -q`、运维 shell 的 `bash -n` 与 Python 编译通过。
- 使用官方 release、SHA-256 校验的 actionlint v1.7.7 检查 `workbench-ci.yml` 与 `workbench-production.yml`，没有错误。
- 本地运行生产凭据门控步骤：缺少 secrets 时输出 `ready=false`，Summary 明确“未部署”，没有生成密钥文件或进行 SSH 连接。
- 本地模拟 GitHub API 元数据验证生产提交门控：成功的最新 main push CI 可发布；过期 main 提交跳过并报告“未部署”；PR 来源、缺少成功 CI 和非 main 历史提交全部拒绝。此模拟不替代将来的真实 GitHub Actions 结果。
- 自动发布强制匹配 main 当前 HEAD，手动发布须填完整 SHA 并通过同仓 main push CI 验证。生产环境部署分支需限制为 main。
- SSH 使用专用密钥与固定 known_hosts，`StrictHostKeyChecking=yes`，无密码交互、无未知主机自动接受。
- 代码包包含 `bedtime.py`、`stories_data.json` 与睡前页面；逐成员检查无 `.env`、用户数据、上传目录、备份、Git 目录或符号链接。
