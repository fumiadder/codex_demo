## 2.2 软件项目开发流程

```python
# 1  6 大阶段：立项需求阶段 → 产品设计阶段 → 开发实施阶段 → 测试阶段 → 上线交付阶段 → 运维迭代阶段

# 2  需要人员：销售 / 售前、项目经理、产品、UI 设计师、前后端开发、移动端、测试、运维、实施


### 阶段 1：立项与需求调研（项目启动）
1. 商务售前对接
销售 + 售前与客户沟通业务痛点、功能范围、预算、交付周期、部署方式
输出：项目技术方案、报价单、合同、投标文件（政企项目）
2. 项目立项
项目经理成立项目组，确定排期、人力分配、里程碑节点
组织启动会，同步客户、产品、研发、测试所有人
3. 需求深度调研
产品经理主导，访谈客户业务人员、负责人：
梳理业务流程、角色权限、报表、第三方对接（支付、短信、OA 等）
区分刚需功能、可选增值功能，划定项目边界，避免需求蔓延
4. 输出交付物
《需求规格说明书 SRS》
简易业务流程图、思维导图
需求评审：客户 + 产品 + 研发 + 测试共同确认，签字锁定需求（变更走变更流程）

## 阶段 2：产品 & UI 设计（上游输出，研发依据）
1. 产品原型设计（PM）
使用 Axure / 墨刀绘制页面原型、交互逻辑、弹窗、表单、菜单
# https://www.axure.com/
# https://modao.cc/
搭建权限体系、数据流转逻辑
输出：原型文件、PRD 产品需求文档（标注字段、校验规则、接口逻辑）

2. UI/UX 视觉设计（设计师）
统一规范：颜色、字体、按钮、表格、弹窗，搭建组件库
输出全套页面效果图、移动端适配页面
制作交互原型、动效说明
交付物：设计源文件、切图、CSS 变量、设计规范文档
3. 技术方案设计（CTO / 架构师）
针对复杂系统输出技术方案：
数据库表结构设计、微服务拆分、接口规范
服务器部署架构、缓存、定时任务、文件存储、安全方案
第三方对接方案、并发、数据备份策略
4. 设计评审会
客户确认 UI 效果；研发评审技术方案，识别技术风险、工期风险；全部确认后进入开发。

## 阶段 3：开发实施阶段（核心编码阶段）
1. 环境搭建（运维 / 后端）
搭建开发环境、测试环境、预发布环境、生产环境
配置 Git 代码仓库、CI/CD 自动构建流水线、Docker 容器服务
2. 分工并行开发
    后端开发
        根据数据库设计建表，编写 RESTful 接口
        实现业务逻辑、权限、文件上传、定时任务、第三方对接
        提供接口文档
    前端开发
        基于 UI 设计稿还原页面，封装公共组件
        对接后端接口，完成表单、列表、弹窗、搜索、导出等功能
        适配 PC 端、平板、手机
        移动端开发（APP / 小程序）
        还原移动端 UI，完成原生 / 跨端页面、推送、相机、本地存储等能力
    联调
    	前后端、移动端联调，修复接口报错、数据展示异常
3. 每日同步管理
每日站会：同步进度、阻塞问题
项目经理跟进里程碑，记录开发工时，出现延期及时调整人力
4. 开发自测
开发完成单个模块后，自行基础功能自测，简单 bug 内部修复，再提交测试。

## 四、阶段 4：测试阶段（质量管控，多层级测试）
1. 提测准入
开发完成当前迭代全部功能，代码合并至测试环境，提供提测单，项目经理确认后转交测试。
2. 分层测试流程
功能测试（手工 QA）
根据需求、原型编写测试用例
全覆盖正常流程、异常场景、边界值、权限校验
提交 Bug 到管理工具（Jira / 禅道），标记严重程度
回归测试
开发修复 Bug 后，测试复测；全部修复完成做完整一轮全功能回归
自动化测试（中大型项目）
接口自动化、UI 自动化脚本，减少重复回归工作量
性能测试（高并发项目）
压测接口响应速度、并发承载量、大数据查询效率
安全测试（政企 / 金融系统）
漏洞扫描、防 SQL 注入、XSS、越权访问，满足等保要求
3. 测试验收报告
所有 Bug 闭环后，输出《测试报告》，标注测试覆盖范围、遗留低风险问题，允许进入预发布。

## 阶段 5：预发布 + 客户验收 + 上线交付
1. 预发布环境验证
复制生产配置，数据模拟真实业务，完整走一遍全流程
项目经理、产品、客户代表共同试用，确认功能符合预期
2. UAT 客户验收
客户方业务人员操作验收，填写验收单；提出的少量优化点记录为迭代需求，不阻碍上线。
3. 生产环境部署上线
运维 / 实施工程师操作：
生产服务器部署程序、数据库迁移
域名、SSL 证书、防火墙、备份策略配置
灰度发布（大型平台）/ 全量发布（小型系统）
上线巡检：检查页面访问、接口、定时任务、文件上传等全部功能
4. 交付资料归档
交付全套项目文档给客户：
需求文档、设计源文件、接口文档、部署手册、运维手册、用户操作手册、源码（私有化项目）

## 阶段 6：运维、售后与迭代维护
1. 上线售后保障
7×12/7×24 技术支持，处理客户使用问题、线上紧急 Bug
定期巡检服务器：CPU、内存、磁盘、日志告警、数据备份校验
2. 版本迭代开发
客户新增需求、功能优化走完整小循环：需求→设计→开发→测试→版本更新上线
3. 项目收尾
质保期结束，完成项目结算；整理项目全套文档归档公司知识库

```

## 3.1 产品经理硬技能

```python
# 1 需求分析与文档输出
## 1.1 需求调研：访谈客户、业务梳理、挖掘真实痛点，区分真假需求、控制需求蔓延【一开始没谈好的新增功能，就是需求蔓延】
## 1.2 文档撰写
```

# 4 产品经理之需求调研
## 4.1 什么是需求调研

```python
# 1 需求调研是产品经理在项目前期，主动通过各类方式和客户、业务人员、终端用户沟通，挖掘真实业务痛点、业务流程、功能诉求、使用限制、隐性期望，并整理、核实、确认，最终形成标准化需求文档的全过程。

# 2 搞清楚客户到底要什么、为什么要、平时怎么干活、系统要帮他解决哪些麻烦。
    显性需求：客户直接说出来的功能，比如 “要一个商品新增页面”；
    隐性需求：客户没说、但业务必须满足的底层逻辑，比如 “商家上架商品后，客户能看到商品”。
```



## 4.2 需求调研重要性

```python
# 1 从根源避免需求蔓延
调研不充分，后期客户不断补充功能、修改逻辑，工期、成本失控，项目亏损。完整调研能一次性锁定业务边界。
# 2 防止做无用功，避免开发完不符合客户预期
没摸清业务就直接画原型、开发，容易出现 “系统功能齐全，但完全不符合客户实际工作流程”，需要大面积返工。
# 3 识别隐藏风险与约束条件
提前发现政策要求、数据安全、第三方对接、硬件限制、并发性能、等保合规等硬性要求，避免开发中途无法实现。
# 4 统一所有人认知
让客户、产品、UI、开发、测试对业务规则达成一致，减少评审、开发阶段反复争执。
# 5 精准划分功能优先级
区分核心刚需、次要优化、远期增值功能，合理规划迭代，保障核心业务先落地。
# 6 降低沟通与维护成本
完整调研产出的流程、规则、文档，可长期留存，新人接手、后期迭代不用重复询问客户。
```

## 4.3 需求调研基本方法

```python
# 1 访谈法（最常用）
一对一 / 多人座谈会沟通，分两类人群访谈：
业务操作人员：日常使用系统的员工，了解操作流程、高频痛点；
管理负责人：老板 / 部门主管，了解管理报表、审批流程、统计分析需求。
操作要点：提前准备调研提纲，多追问 “为什么这么做”，不只记录表面需求。

# 2  现场跟班观察法（ToB / 政企 / 工厂项目必备）
实地跟着客户员工完整走一遍工作流程，看真实业务操作：
例如医院收费、工厂车间、政务窗口、门店收银。
优势：能发现客户自己都意识不到的隐性痛点。

# 3 资料研读法
收集客户现有资料，梳理业务规则：
纸质单据、Excel 台账、旧系统截图、现有管理制度、合同、审批单、报表模板、行业政策文件。
直接拿现有单据作为系统字段、表格、导出报表的设计依据。

# 4 问卷调研法
适合大量终端用户、C 端产品、多门店统一收集需求；
制作标准化问卷，批量收集用户使用痛点与功能偏好，适合统计量化需求。

# 5 原型引导调研（高效手段）
先用 原型软件 快速出简易低保真原型，拿着原型和客户逐条核对；
客户能直观看到页面，更容易发现遗漏、提出修改意见，比纯文字沟通效率更高。

# 6 竞品对标调研
调研同行业成熟系统，参考通用标准功能、成熟业务流程；
避免重复踩坑，同时可以向客户提供行业标准化解决方案。

# 7 原型试用 + 演示沟通
若客户有旧系统，让客户完整演示旧系统操作，记录现有短板、想要优化点。
```



# 5 产品经理之需求分析
## 5.1 什么是需求分析

```python
# 1  需求调研收集完客户、业务、用户的零散诉求后，产品经理【拆解、梳理、校验、提炼、标准化】诉求的过程，就是需求分析。
	-把一堆杂乱的口头想法、零散单据，转化成可落地、无矛盾、逻辑通顺、有价值的产品功能。

# 2 核心工作：
    1. 剔除重复、矛盾、无价值诉求；
    2. 区分表层诉求和底层真实痛点；
    3. 梳理业务流程、数据流转、权限、异常场景；
    4. 把需求转化为原型、PRD 可开发内容；
    5. 识别技术、成本、工期风险。
```



## 5.2 识别真需求 vs 规避伪需求

```python
# 1  核心定义
真需求：背后有真实业务痛点，解决后能降本、增效、合规、增收，用户愿意长期使用，不做会严重影响业务运转。
伪需求：只是用户临时想法、个人偏好、片面设想，实现后无法产生实际价值，甚至增加操作负担、浪费开发资源。

# 2 4 个判断标准，快速区分真假需求
## 标准 1：追问底层动机（5Why 分析法）
用户说：“我想要 XX 功能”，连续问 5 层为什么：
例：客户说 “后台要做一个复杂的颜色标记区分订单”
Why1：为什么要标记订单？→方便快速筛选
Why2：为什么筛选？→每天要导出报表统计异常单
Why3：现有系统不能筛选吗？→筛选条件太少
Why4：缺哪些条件？→缺少支付状态、发货时间筛选
Why5：增加筛选框能不能解决？→可以，比颜色标记更高效
结论：客户想要 “颜色标记” 是表层方案（伪诉求），多条件筛选才是真需求。

## 标准 2：是否对应稳定、高频业务场景
真需求：每天 / 每周固定要操作，不做业务跑不通；
伪需求：一年只用 1 次、临时特殊场景、个人喜好。

## 标准 3：投入产出是否匹配
开发耗时久、人力成本高，但几乎不提升效率、不解决核心痛点 → 大概率伪需求。

## 标准 4：多人统一诉求还是单人主观想法
真需求：一线操作人员、管理人员普遍存在的共同痛点；
伪需求：仅某个领导 / 单个员工个人习惯，其他人无需求。


# 3  规避伪需求实操手段
不听用户给的 “解决方案”，只抓背后 “痛点”；
现场实地观察业务，不单纯依赖口头描述；
需求落地前用简易原型验证，快速试错；
新增需求统一放入需求池，不直接插入当前迭代；
任何需求都明确使用人群、使用频次、业务价值，无价值直接驳回
```



## 5.3 需求池 & 需求池分类

```python
# 1 需求池定义
统一存放所有收集到需求的台账 / 表格 / Jira 清单，是产品管理所有诉求的容器。
来源包含：客户提出、内部运营、销售、开发建议、用户反馈、竞品优化、bug 衍生优化、规划新功能。
作用：统一管理、避免遗漏、集中评审、控制需求蔓延，所有改动不走口头沟通。


# 2 需求池常用 4 大分类
## 2.1 业务刚需需求（核心功能）
项目上线必须具备，缺失则业务无法正常运转，合同约定交付内容。
例：商城下单、审批流程、数据台账、报表统计。
## 2.2 优化迭代需求（体验提升）
现有功能能用，但操作繁琐、体验差，优化后提升效率，不影响基础业务。
例：增加批量导入、简化表单填写、页面加载提速。
## 2.3 新增增值需求（二期 / 远期）
不在当前项目范围，锦上添花功能，当前版本不做，放入后续版本规划。
例：分销、会员、营销活动、复杂可视化大屏。
## 2.4 缺陷修复需求（Bug 类）
系统逻辑错误、页面异常、数据计算错误，优先级通常很高。
```

## 5.4 需求优先级安排

```python
# 方法 1：MoSCoW 法则（项目定制 / 政企软件最常用）
M Must have 必须做（最高优先级）
刚需，当前迭代 / 版本必须交付，缺了项目无法验收。
S Should have 应该做（次高）
大幅提升业务效率，有显著价值，本周期尽量实现；时间不足可小幅延后。
C Could have 可以做（低优先级）
提升体验，无硬性要求，工期紧张直接砍掉，放到下一版。
W Won’t have 暂不做（最低）
价值低、成本高，本期完全不开发，存入需求池远期规划。


# 方法 2：价值成本矩阵（互联网 SaaS 产品常用）
两个维度打分：业务价值（高 / 低）、开发成本（高 / 低）
高价值 + 低成本 → 立刻做（优先）
高价值 + 高成本 → 规划重点迭代，拆分小模块分步实现
低价值 + 低成本 → 空闲顺带优化
```
