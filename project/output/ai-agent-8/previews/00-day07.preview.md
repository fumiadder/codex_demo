# 1 产品经理之竞品分析
## 1.1 什么是竞品分析

```python
# 1 竞品分析，就是对标同行业同类软件 / 产品，系统性拆解对方的产品功能、业务流程、页面交互、商业模式、优缺点，用来支撑自家产品规划、需求设计、差异化定位的调研工作。

# 2 核心目的
    摸清行业通用标准，避免重复踩坑；
    找到竞品短板，打造自己产品的差异化优势；
    借鉴成熟好用的交互、流程，降低设计和开发试错成本；
    给老板、客户、研发提供依据，证明功能设计合理；
    预判行业趋势，规划中长期产品迭代方向。
# 3 竞品分为三类
直接竞品：业务、目标客户、终端完全一样。
	例：做政务 OA，其他厂商政务 OA 系统；做商城小程序，其他商城小程序。
间接竞品：解决同一类痛点，但产品形态不同。
	例：线下 Excel 台账 VS 线上 CRM 管理系统。
标杆竞品：行业头部标杆，不直接竞争，但体验、架构值得学习参考。
```

## 1.2 竞品分析报告如何编写

```python
# 1 报告概述（开篇）
分析背景：为什么做本次竞品分析（新项目立项 / 版本迭代 / 客户提出优化）
分析目标：本次要解决什么问题
竞品选取清单：列出 3～5 款竞品，标注类型（直接 / 间接 / 标杆）
分析范围：本次只对比哪些模块（如订单管理、报表、小程序、审批流程）
数据来源：官网、试用账号、公开演示、行业资料、客户使用反馈

# 2 竞品基础信息对比表
用表格统一罗列基础维度，一目了然-->如下图

# 3  核心模块详细拆解（报告主体，最重要）：按产品模块逐一拆解，每个模块包含 4 部分
    -竞品功能流程：业务流转逻辑、页面结构
    -交互设计：新增编辑弹窗、筛选、批量操作、导出、权限控制
    -亮点设计：值得借鉴的功能、便捷交互
    -缺点与痛点：客户使用不方便、逻辑不合理之处
    
# 4 用户体验 & 视觉交互分析
    -页面布局、导航菜单结构
    -操作步骤多少，是否多页面跳转
    -表单校验、异常提示、加载反馈
    -设计规范：组件、色彩（可附截图）
    -适配性：手机、平板、大屏兼容情况
    
# 5 商业模式 & 运营能力分析（ToC/SaaS 重点，政企可简化）
    客户获取方式、套餐版本区分
    增值付费模块（报表、多端、定制化）
    配套服务：实施培训、售后、升级迭代政策
    
# 6 整体总结：竞品共性 & 差异化机会点
    （1）行业通用共性（行业标配功能，我方必须具备）
    所有竞品都有的基础功能，属于行业门槛，缺失会被客户淘汰。
    （2）竞品共同短板（我方差异化突破口）
    多家竞品都没做好的点，作为产品核心亮点。
    （3）竞品独有优势（需要对标补齐）
    头部竞品特色功能，客户关注度高，后续迭代规划实现。
# 7 落地行动建议（报告最终产出价值）
分三类需求放入需求池，明确优先级：
    本期必做：行业标配刚需，不做无法交付 / 竞争
    本期优化：借鉴竞品优秀交互，提升现有功能体验
    中长期规划：竞品特色增值功能，放到二期迭代
    舍弃不做：竞品低效、冗余功能，避免资源浪费
# 8 附录
附上竞品页面截图、流程草图、原型截图、参考资料链接。

##########总结##########
竞品分析 = 摸清行业标准 + 找到对手弱点，用来决定我们产品该做什么、不该做什么、怎么做更好
```

# 2 产品经理之项目规划书
## 2.1 项目规划书是什么

```python
# 1 项目规划书 = 整个项目的 “总说明书 + 施工总方案”
告诉所有人：这个项目要做什么、多久做完、谁来做、怎么做、风险是什么、交付什么结果。

# 2 它是项目启动后第一份正式文档，是所有开发、设计、测试、交付的总纲领。

# 3 项目规划书 = 项目整体怎么干（给公司、客户、团队全员看）
```



## 2.2 项目规划书作用

```python
# 1 锁定项目范围
防止需求蔓延，写清楚做什么、不做什么。
# 2 统一所有人节奏
设计、研发、测试、实施,运维、客户所有人对齐工期。
# 3 规避风险
提前写技术风险、人员风险、延期风险、对接风险。
# 4 作为验收依据
后期客户扯皮、延期、变更，全部以规划书为凭证。
# 5 管理层用来考核项目进度

```

## 2.3 项目规划书标准包含内容

```python
# 1 项目概述
    项目名称
    项目背景、建设目的
    解决的业务痛点
    项目价值（降本、增效、合规、数字化）
# 2 项目建设范围（核心！防需求蔓延）
    包含功能模块
    包含终端（Web、小程序、APP、大屏）
    明确不包含哪些功能（最重要！防扯皮）
# 3 项目目标
    功能目标
    进度目标
    质量目标
    安全、合规目标
# 4 项目人员组织架构
    项目经理、产品、UI、前端、后端、测试、实施、运维
    每个人职责分工
# 5 项目整体实施流程
立项 → 需求调研 → 设计 → 开发 → 测试 → 验收 → 上线运维

# 6 项目里程碑排期（核心）
明确每个阶段起止时间、产出物
比如：
    需求阶段：3 天，输出 PRD、流程图
    UI 设计：5 天，输出全套设计稿
    开发：15 天
    测试：5 天
    上线验收：2 天
# 7  项目交付物清单
所有要交付给客户的资料：
原型、PRD、设计稿、源码、部署手册、用户手册、测试报告

# 8 项目风险评估 & 应对方案
常见风险：
    客户需求频繁变更
    第三方接口不稳定
    工期紧张、人员不足
    客户配合度低
    	每条风险写：风险 + 影响 + 应对方案
        
# 9 需求变更管理机制
明确：所有变更必须走变更流程，不能口头加需求，用来控制需求蔓延
# 10 质量保障方案
代码规范、测试策略、回归策略、Bug 修复标准
# 11 验收标准
明确：达到什么标准算项目完成
```

```python
# 2  顺序：
立项 → 输出《项目规划书》→ 需求调研 → PRD → 开发
```



# 3 产品经理之产品需求文档-PRD
## 3.1 什么是 PRD？

```python
# 1 PRD（Product Requirement Document）产品需求文档

# 2 是产品经理输出的【落地级、执行级、施工级】官方文档
	-PRD 是给 UI、开发、测试、实施看的“产品施工图纸”
    
# 3 它把客户杂乱的需求、业务流程、口头想法，整理成：
    - 每个页面
    - 每个按钮
    - 每个字段
    - 每条逻辑
    - 每种状态
    - 每个异常场景
    
    
	-抖音转小红书文案 产品
    	-注册，登陆，首页，结果
        -注册：用户名，密码，确认密码，注册按钮，去登陆按钮
        -首页：文字描述：输入框 按钮
        
    -绝大部分同学有产品能力，但是不是一个好产品
    	-真正的工作经历
        
# 4 让技术团队【不用猜、不用问、直接照着做】
```



## 3.2 PRD 的核心作用与价值

```python
# 1 统一团队认知，消除沟通扯皮
开发、测试、UI、客户理解的需求经常不一样，PRD 是唯一标准，所有人以文档为准，杜绝“我以为、我觉得、你没说”。

# 2 作为开发、测试的唯一施工依据
开发照着 PRD 写代码，测试照着 PRD 写用例、验收功能。没有 PRD 就是瞎开发、盲测试。

# 3 锁定需求范围，控制需求蔓延
PRD 评审通过后 = 需求冻结
后期客户临时新增需求，全部属于变更需求，不走当前版本，避免项目无限延期、无限加班。

# 4 规避返工风险，降低项目成本
需求写得越细，返工越少。80% 的项目返工，都是因为 PRD 缺失、逻辑不全、场景遗漏。

# 5 作为验收、交付、追责的依据
项目验收、后期扯皮、功能对不上，全部以 PRD 为准。

# 6 项目沉淀资产，方便迭代交接
新人接手、版本迭代、二次开发，不用反复问老员工，直接看 PRD。
```



## 3.3 PRD 标准编写要求与规范

```python
# 1 逻辑完整性（最重要）
一个完整功能必须包含：
    - 新增、编辑、删除、查询、详情
    - 字段说明、字段校验、必填/非必填
    - 状态流转（待审核、已通过、已驳回）
    - 按钮权限、角色可见性
    - 异常场景、空数据场景、报错提示
    - 数据联动、自动计算、默认值
严禁只写“简单描述”，不写细节。
# 2 精准无歧义
杜绝：大概、可能、酌情、相关设置、相应提示
所有描述必须唯一、确定、没有第二种理解。
# 3 场景全覆盖
不仅写正常操作，必须写：
    - 空数据场景
    - 超限场景
    - 权限不足场景
    - 重复提交场景
    - 失败回滚场景
    
# 4 图文结合，绑定原型
PRD 必须搭配 Axure 原型链接
文字讲逻辑，原型讲页面，二者缺一不可。
# 5 结构统一、模块化
所有模块统一格式，方便开发快速阅读，不混乱。
# 6 可开发、可测试、可验收
好的 PRD 标准：开发看完直接写代码，测试看完直接写用例。
凡是需要再问产品的，都是不合格 PRD。
```

## 3.4 PRD 必须包含的结构

```python
# 1 产品整体概述：功能目的、适用用户、业务价值
# 2 业务流程图：完整流转逻辑
# 3 全局规则：权限、状态、字典、通用交互
# 4 页面详细需求：每个页面、每个按钮、字段说明
# 5 数据规则：默认值、联动、计算、排序
# 6 异常规则：报错、提示、空页面、拦截逻辑
# 7 权限规则：哪些角色可见、可操作
# 8 接口说明（简要）：需要哪些对接能力
# 9 版本更新记录：变更记录留痕
```

# 4 产品经理之需求评审
## 4.1 什么是需求评审

```python
# 1 需求评审是产品完成原型、PRD 之后，由产品经理牵头，组织项目经理、UI、前后端开发、测试（政企项目加客户业务方）开展的正式评审会议。

# 2 流程：
# 2.1 产品完整讲解业务流程、页面逻辑、交互、数据规则、权限、异常场景；
# 2.2 各角色针对文档、原型提出疑问、逻辑漏洞、技术实现难点、不合理交互；
# 2.3 当场讨论并记录所有问题，会后产品更新 PRD、原型；
# 2.4 所有人确认无误后，需求冻结，这份文档成为开发、测试、验收唯一标准。

通俗比喻：施工前所有人一起核对施工图纸，提前找出图纸错误，再动工。
```



## 4.2 需求评审的重要性

```python
# 1 统一所有人对需求的认知，消除理解偏差
产品、开发、测试、客户单独看文档容易产生不同理解。评审一次性同步全部业务规则，避免后期出现 “理解不一致” 的矛盾。

# 2 提前发现需求漏洞，大幅减少返工成本
    测试会指出缺失边界、异常、校验逻辑；
    开发会指出逻辑冲突、技术不可行、性能隐患；
    图纸阶段修改需求成本极低；等到代码写完再改，工时、人力成本会成倍增加。
    
# 3 提前识别技术风险，合理评估工期
开发可以提前识别复杂功能、第三方对接、高并发等难点；项目经理根据完整需求重新评估工作量，避免前期排期低估导致项目延期。

# 4 锁定项目范围，管控需求蔓延
评审确认后的需求为基准，后续客户临时新增、修改功能统一走需求变更流程，不随意加入当前迭代，从源头防止范围无限扩大。

# 5 明确验收标准，减少交付纠纷
评审时各方对齐功能标准，后期客户验收不会随意提出全新要求，降低验收扯皮、回款困难风险。

# 6 集中答疑，降低后续碎片化沟通成本
跳过评审会导致开发、测试在开发过程中反复单独找产品确认细节，打断工作节奏；一次评审集中解决全部疑问，提升整体研发效率。

# 7 形成可追溯的正式项目资料
评审记录、修改痕迹、确认版 PRD 留存归档，人员交接、版本迭代、项目复盘都有据可查。
```



# 5 产品经理之技术评审
## 5.1 什么是技术评审

```python
# 1 技术评审（同行评审）是以技术人员为核心，针对技术方案、架构设计、数据库、接口、代码、测试方案、部署方案开展的专业审查会议，聚焦“怎么实现”，判断技术方案是否可行、合理、安全、高性能。

# 2 核心定位区分
## 2.1 需求评审：产品牵头，确认做什么，核对业务功能、页面逻辑、客户诉求；参会：产品、UI、开发、测试、客户。
## 2.2 技术评审：架构 / 后端负责人牵头，确认怎么做，核对技术落地细节；参会：架构师、前后端开发、DBA、测试、运维，产品仅列席对齐需求。

# 3 常见 4 类技术评审场景
## 3.1 架构方案评审：项目整体技术架构、微服务、第三方对接、部署方案；
## 3.2 详细设计评审：数据库表结构、模块拆分、接口规范、核心业务流程；
## 3.3 代码评审（Code Review）：开发写完模块后，同行检查代码规范、逻辑漏洞、性能问题；
## 3.4 测试方案评审：测试范围、自动化策略、压测、安全测试方案。
```



## 5.2 技术评审主要检查内容

```python
# 1 架构层面：技术选型是否成熟、分层 / 微服务划分是否合理、模块耦合度是否过高；
# 2 数据库设计：表、字段、主键、索引、关联关系、分表策略、数据冗余；
# 3 接口设计：RESTful 规范、入参出参、异常返回、分页、权限校验；
# 4 业务逻辑：状态流转、数据联动、事务处理、重复提交拦截；
# 5 性能：大数据查询、高并发场景、缓存策略、定时任务；
# 6 安全：登录鉴权、数据脱敏、防注入、文件上传校验、内网访问控制；
# 7 可维护性：代码复用、注释、日志、错误告警、便于后续迭代；
# 8 部署运维：环境隔离、CI/CD、数据备份、监控告警、私有化部署方案。
```

## 7.1 原型图是什么

```python
# 0 原型图需要产品使用软件：墨刀，axure，figma等，操作画出来
	-我们后续课程使用AI帮我们完成，我们只做调整
    
# 1 定义
原型图是产品经理在开发前绘制的产品页面模拟草图，用来还原页面布局、按钮、输入框、弹窗、跳转逻辑、交互流程，不做精美视觉，只表达功能结构与操作逻辑，是 UI 设计、开发、测试的参考依据。

# 2 核心作用
可视化需求，把文字 PRD 变成看得见的页面，客户、研发更容易看懂；
提前验证业务流程、页面跳转逻辑，提前发现逻辑漏洞；
作为 UI 设计师做视觉稿的基准；
需求评审核心材料，统一所有人对页面结构的认知；
快速修改调整，成本远低于开发完成后返工。

# 3 两种原型区分
## 低保真原型（线框图）
只有方框、文字、按钮，无色彩、无真实图片，仅表达布局，Axure、ProcessOn、墨刀都能做，需求阶段最常用。
## 高保真原型
```

```python
# 1 Axure RP（企业 PM 标配，最专业）
```

## 8.2 Figma ,Axure,墨刀的区别

```python
# 1 区别
墨刀：国内新手快速画简易原型，手机 APP、小程序快速出演示稿，主打简单、快、全中文
Axure：专业产品经理老工具，专门做复杂后台、多层逻辑、数据表格，能模拟真实系统全套业务规则
Figma：UI 设计师专用，画最终上线精美界面，做统一设计规范，原型只是附带功能
# 2 上手难度对比
墨刀：最简单，拖拽现成组件，零基础 1 小时做出可点击原型，原生中文
Figma：中等，功能多，要学组件、自动布局，原版英文，需要汉化
Axure：最难，逻辑功能一堆，变量、动态面板、中继器概念复杂，学习周期很长

# 3  交互逻辑能力
## 墨刀
只有基础功能：页面跳转、弹窗、轮播，内置现成组件不用自己写逻辑；
适合简单 APP、小程序，复杂表单、多权限后台会吃力。
## Axure（逻辑天花板）
自带 “迷你编程” 能力：
登录判断、输错密码锁定账号
后台表格筛选、分页、增删数据
多角色看到不同页面、满减计算、多层弹窗嵌套
B 端管理系统、金融后台、复杂流程首选，别的工具比不了。

## Figma
交互弱，只能做简单页面切换、小弹窗动画；
做不了复杂业务判断，只用来展示界面长什么样。

# 4  画面美观度（能不能做上线成品）
Figma 最强：矢量绘图、调色、插画、组件库、像素级精细，最终交给前端开发的正式视觉稿全靠它
墨刀 中等：能做中等好看的原型，但自定义样式受限，复杂设计很别扭
Axure 最差：原生界面简陋，主要画线框图，不适合做精美视觉

# 5 使用方式、网络、协作
## 墨刀
网页云端，国内访问丝滑，发链接就能共享，手机扫码真机演示；
免费版够用，付费便宜，国产合规，国企、传统企业能用。

## Figma
网页 + 桌面客户端，国外服务器，国内经常加载慢；
多人实时同时改一张设计稿，设计师协作无敌；
文件存在海外，很多国内大企业禁用。

## Axure
纯本地桌面软件，无云端，文件存在电脑里；
分享要导出 HTML 文件发给别人，没法在线实时批注；
断网完全能用，离线无敌，买断制一次性付费。

# 6 价格模式
墨刀：免费版有项目限制，按月会员，价格便宜
Figma：免费个人版限 3 个私有文件，团队按月订阅（海外付费）
Axure：一次性买断，无永久免费版，价格贵
```
